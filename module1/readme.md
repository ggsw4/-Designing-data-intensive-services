### 1.1. FastAPI: современный фреймворк для построения API

**FastAPI** — это современный Python-фреймворк для создания REST API, созданный Себастьяном Рамиресом (известным как Tiangolo). Он построен на двух ключевых библиотеках: **Starlette** (ASGI-фреймворк для маршрутизации и обработки запросов) и **Pydantic** (библиотека валидации данных на основе аннотаций типов).

**Ключевые преимущества FastAPI:**

| Преимущество | Что это означает на практике |
|---|---|
| **Высокая производительность** | Один из самых быстрых Python-фреймворков благодаря ASGI и Uvicorn |
| **Типизация** | Аннотации типов Python автоматически становятся валидацией запросов через Pydantic |
| **Автодокументация** | Интерактивная Swagger UI доступна по адресу `/docs` без дополнительных усилий |
| **Асинхронность** | `async def` поддерживается нативно для I/O-bound эндпоинтов |
| **Стандарт OpenAPI** | Генерирует спецификацию, совместимую с инструментами тестирования |

**Почему FastAPI выбран для нашего курса:**

FastAPI — это де-факто стандарт для создания API на Python в 2025–2026 годах. Он используется в продакшене таких компаний, как Microsoft, Netflix, Uber и других. Для высоконагруженных сервисов критически важна асинхронная модель, которую FastAPI поддерживает «из коробки».

### 1.2. Uvicorn: ASGI-сервер

**Uvicorn** — это молниеносно быстрый ASGI-сервер для Python, построенный на библиотеках **uvloop** (быстрая реализация event loop на Cython) и **httptools** (быстрый парсер HTTP на C).

**Роль Uvicorn в стеке:**

Uvicorn выступает в роли «двигателя», который принимает HTTP-запросы от клиентов и передаёт их в приложение FastAPI. Без ASGI-сервера приложение FastAPI не может обрабатывать реальные сетевые запросы — оно существует только как Python-код.

**Установка:**

```bash
pip install "fastapi[standard]"
```

Опция `[standard]` автоматически устанавливает Uvicorn, httpx (для тестирования), email-validator и CLI-инструменты FastAPI. Для быстрого старта это правильный выбор.

**Запуск сервера:**

```bash
fastapi dev main.py
```

Эта команда запускает сервер на `localhost:8000` с автоматической перезагрузкой при изменении кода (hot-reload).

### 1.3. ASGI и WSGI: в чём разница и почему это важно

**WSGI (Web Server Gateway Interface)** и **ASGI (Asynchronous Server Gateway Interface)** — это два стандарта, которые определяют, как Python-веб-сервер общается с веб-приложением.

**Аналогия с тортом:**

Представьте, что вам нужно испечь торт и приготовить крем. Это две задачи.

**WSGI (синхронный подход):** Вы должны полностью завершить первую задачу, прежде чем начать вторую. Пока торт печётся 30 минут, вы стоите и ждёте. Только после того, как торт готов, вы начинаете делать крем.

**ASGI (асинхронный подход):** Вы ставите торт в духовку и, пока он печётся, начинаете делать крем. Когда торт готов, вы возвращаетесь к нему. Вместо простоя вы делаете полезную работу.

**Техническое различие:**

| Характеристика | WSGI | ASGI |
|---|---|---|
| **Модель обработки** | Синхронная: один запрос за раз | Асинхронная: несколько запросов одновременно |
| **Протоколы** | Только HTTP | HTTP, WebSocket, SSE, фоновые задачи |
| **Примеры фреймворков** | Flask, Django (традиционный) | FastAPI, Starlette, Django (ASGI) |
| **Пропускная способность** | ~1 запрос за раз | Множество одновременных запросов |

**Почему это важно для высоконагруженных систем:**

При нагрузочном тестировании мы увидим, что ASGI-приложение (FastAPI + Uvicorn) обрабатывает значительно больше запросов в секунду, чем эквивалентное WSGI-приложение (Flask + Gunicorn). Это прямое следствие асинхронной модели: пока один запрос ждёт ответа от базы данных, event loop переключается на обработку другого запроса.

### 1.4. Asyncio: event loop и корутины

**Asyncio** — это библиотека Python для написания конкурентного кода с использованием синтаксиса `async`/`await`. В основе asyncio лежит **event loop** (цикл событий) — центральный механизм, который управляет выполнением асинхронных задач.

**Event loop** — это, по сути, «дирижёр оркестра». Он содержит очередь задач и поочерёдно запускает их. Когда задача встречает операцию ввода-вывода (например, сетевой запрос или чтение файла), она «приостанавливается» и возвращает управление event loop. Event loop немедленно переключается на следующую задачу. Когда операция ввода-вывода завершается, приостановленная задача возобновляется.

**Корутина** — это функция, определённая с помощью `async def`. Она может приостанавливать своё выполнение в точках `await` и возобновляться позже. Корутина представляет собой тело функции или её логику.

**Ключевое правило для FastAPI:**

Если ваш эндпоинт выполняет только неблокирующие операции (например, асинхронные запросы к БД через `asyncpg`), используйте `async def`. Если эндпоинт содержит блокирующий код (например, `requests.get()` или синхронный запрос к БД), использование `async def` сделает хуже, чем обычный `def`, потому что вы «пообещаете» event loop, что не будете блокировать, но нарушите это обещание.

FastAPI обрабатывает `def`-эндпоинты в отдельном пуле потоков (threadpool), что позволяет им выполняться конкурентно, не блокируя event loop. Для нашей практической работы мы будем использовать `async def` с неблокирующими операциями.

### 1.5. Locust: инструмент нагрузочного тестирования

**Locust** — это open-source инструмент для нагрузочного тестирования, написанный на Python. Его ключевое преимущество: тесты — это обычный Python-код, а не XML или бинарный формат. Это делает их гибкими, версионируемыми и легко интегрируемыми в CI/CD.

**Как работает Locust:**

Locust использует модель «пользователей» (users). Каждый пользователь — это greenlet (легковесный поток), который выполняет определённые задачи (tasks) с заданной периодичностью. Вы можете запустить сотни или тысячи одновременных пользователей, чтобы имитировать реальную нагрузку.

**Установка:**

```bash
pip install locust
```

**Базовый тест:**

```python
# locustfile.py
from locust import HttpUser, task, between

class WebsiteUser(HttpUser):
    wait_time = between(1, 3)  # Пауза 1-3 секунды между задачами

    @task
    def health_check(self):
        self.client.get("/health")

    @task(3)  # Вес 3 — выполняется в 3 раза чаще
    def root(self):
        self.client.get("/")
```

Запуск:

```bash
locust --host=http://localhost:8000
```

После запуска откройте `http://localhost:8089` в браузере, укажите количество пользователей и скорость их появления (spawn rate), и начните тест.

### Шаг 2. Создание базового FastAPI-сервиса (20 минут)

**2.1. Создайте файл `main.py`:**

```python
from fastapi import FastAPI
from datetime import datetime

app = FastAPI(
    title="Highload Shop API",
    description="Базовый сервис интернет-магазина для нагрузочного тестирования",
    version="0.1.0"
)

@app.get("/")
async def root():
    """Корневой эндпоинт — имитация главной страницы."""
    return {
        "service": "highload-shop",
        "status": "running",
        "timestamp": datetime.utcnow().isoformat()
    }

@app.get("/health")
async def health_check():
    """Эндпоинт проверки здоровья сервиса."""
    return {"status": "healthy"}

@app.get("/products")
async def list_products():
    """Имитация списка товаров."""
    return {
        "products": [
            {"id": 1, "name": "Ноутбук", "price": 89990},
            {"id": 2, "name": "Смартфон", "price": 49990},
            {"id": 3, "name": "Наушники", "price": 12990}
        ],
        "total": 3
    }

@app.get("/products/{product_id}")
async def get_product(product_id: int):
    """Имитация получения товара по ID."""
    return {
        "id": product_id,
        "name": f"Товар #{product_id}",
        "price": 10000 + product_id * 1000
    }
```

**Разбор кода:**

- `FastAPI(...)` — создание приложения с метаданными. Эти метаданные будут отображаться в автоматически генерируемой документации Swagger UI по адресу `/docs`.
- `@app.get("/")` — декоратор, который связывает HTTP GET-запрос к пути `/` с функцией `root()`. FastAPI автоматически преобразует возвращаемый словарь в JSON-ответ.
- `async def` — все эндпоинты объявлены асинхронными. Это важно для I/O-bound задач, хотя в данной работе эндпоинты не выполняют реальных I/O-операций. Мы закладываем правильную архитектуру с самого начала.
- `/health` — выделенный эндпоинт для проверки здоровья. Это стандартная практика в индустрии: health-check должен быть лёгким и не затрагивать внешние зависимости.

### Шаг 3. Нагрузочное тестирование с помощью Locust (20 минут)

**3.1. Создайте файл `locustfile.py`:**

```python
from locust import HttpUser, task, between

class ShopUser(HttpUser):
    """
    Имитация пользователя интернет-магазина.
    Пользователь выполняет задачи с паузой 1-3 секунды между ними.
    """
    wait_time = between(1, 3)

    @task(5)  # Вес 5 — самая частая задача
    def view_products(self):
        """Просмотр списка товаров."""
        self.client.get("/products")

    @task(3)  # Вес 3 — средняя частота
    def view_product(self):
        """Просмотр конкретного товара."""
        product_id = 1  # В реальном тесте можно рандомизировать
        self.client.get(f"/products/{product_id}")

    @task(1)  # Вес 1 — редкая задача
    def health_check(self):
        """Проверка здоровья (редко в реальной жизни)."""
        self.client.get("/health")
```

**Разбор кода:**

- `HttpUser` — базовый класс для HTTP-пользователей. Locust создаёт экземпляр этого класса для каждого виртуального пользователя.
- `wait_time = between(1, 3)` — каждый пользователь ждёт случайное время от 1 до 3 секунд между задачами. Это имитирует поведение реального пользователя.
- `@task(5)` — декоратор с весом. Вес 5 означает, что эта задача выполняется в 5 раз чаще, чем задача с весом 1.
- `self.client.get(...)` — выполнение HTTP GET-запроса. Locust автоматически измеряет время ответа и статус-код.

**3.2. Запустите Locust:**

```bash
locust --host=http://localhost:8000

```

**3.3. Откройте веб-интерфейс:**

Перейдите по адресу `http://localhost:8089`. Вы увидите форму с параметрами:

- **Number of users:** количество одновременных пользователей (начните с 10)
- **Spawn rate:** сколько пользователей добавляется в секунду (начните с 1)

**3.4. Запустите тест:**

Нажмите «Start swarming». Locust начнёт создавать виртуальных пользователей и выполнять задачи.

**3.5. Наблюдайте за метриками:**

Locust в реальном времени отображает:

- **RPS (Requests per Second):** пропускная способность
- **Response times:** среднее время ответа, p50, p95, p99
- **Number of failures:** количество ошибок

**Объяснение метрик:**

**p50 (медиана)** — половина запросов выполнена быстрее этого времени. Это «типичный» пользователь.

**p95** — 95% запросов выполнены быстрее. Это ключевая метрика для SLA: если p95 latency превышает 500 мс, большинство пользователей чувствуют дискомфорт.

**p99** — 99% запросов выполнены быстрее. Это «хвост» распределения. Высокий p99 указывает на проблемы с отдельными запросами (например, из-за сборки мусора или конкуренции за ресурсы).

**3.6. Проведите серию тестов:**

Проведите как минимум три теста с разным количеством пользователей:

| Тест | Пользователей | Spawn rate | Цель |
|---|---|---|---|
| A | 10 | 1 | Базовый уровень, низкая нагрузка |
| B | 50 | 5 | Средняя нагрузка |
| C | 100 | 10 | Высокая нагрузка, поиск предела |

**3.7. Зафиксируйте результаты:**

Для каждого теста запишите:

- RPS (средний и пиковый)
- p50, p95, p99 latency
- Error rate (процент ошибок)
- Время, за которое система достигла saturation

### Шаг 4. Анализ результатов (10 минут)

**4.1. Постройте графики:**

В веб-интерфейсе Locust перейдите на вкладку **Charts**. Вы увидите:

- График RPS во времени
- График response times во времени
- График количества пользователей

**4.2. Найдите точку saturation:**

Точка saturation — это момент, когда:

- RPS перестаёт расти, несмотря на увеличение количества пользователей
- Response time начинает резко расти
- Появляются ошибки (таймауты, 5xx)

**4.3. Интерпретируйте результаты:**

Ответьте на вопросы:

1. **Какой RPS у сервиса при 10 пользователях?** Это базовая пропускная способность.
2. **При каком количестве пользователей latency начинает деградировать?** Это точка, после которой система приближается к saturation.
3. **Какая метрика деградирует первой: p50, p95 или p99?** Обычно p99 растёт первым, потому что «хвостовые» запросы страдают от конкуренции за ресурсы.
4. **Есть ли ошибки?** Если да, при каком уровне нагрузки они появляются?

**4.4. Сравните эндпоинты:**

Посмотрите на статистику по каждому эндпоинту отдельно (вкладка **Statistics**). Какой эндпоинт самый медленный? Почему?

В нашем случае все эндпоинты выполняются одинаково быстро, потому что они не делают реальных I/O-операций. Но в последующих модулях, когда мы добавим базу данных и кеш, разница станет очевидной.

| Высокий p99 при низком p50 | Проблемы с «хвостовыми» запросами | Проверьте, нет ли блокирующих операций в эндпоинтах |

## Связь с последующими модулями

Это практическое задние закладывает основу для всего курса:

- **Модуль 2 (Сеть и балансировка):** Мы добавим Nginx как reverse proxy перед несколькими экземплярами этого сервиса.
- **Модуль 3 (Базы данных):** Эндпоинты будут читать данные из PostgreSQL, и мы увидим, как это влияет на latency.
- **Модуль 4 (Кеширование):** Добавим Redis для кеширования списка товаров и сравним производительность с холодным и тёплым кешем.
- **Модуль 5 (Очереди):** Добавим Kafka для асинхронной обработки заказов.

Таким образом, сервис, созданный в этой работе, станет основой для сквозного проекта, который будет развиваться на протяжении всего курса.
